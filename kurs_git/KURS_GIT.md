# Git для чайников: короткий курс простым языком

Главная мысль курса: **Git — это «сохранялки» для папки с файлами.** Как в игре: дошёл до важного места — сохранился. Испортил — загрузился с сохранения. Всё остальное в Git — это удобства вокруг этой идеи.

Курс идёт по шагам. Каждый урок опирается на предыдущий, поэтому лучше читать по порядку и сразу пробовать команды руками.

## Урок 0. Зачем это вообще нужно

Знакомая картина:

```
сценарий.docx
сценарий_новый.docx
сценарий_новый_ФИНАЛ.docx
сценарий_новый_ФИНАЛ_точно_последний.docx
```

Git решает именно эту проблему. Файл остаётся **один**, а все прошлые версии Git хранит у себя внутри. В любой момент можно:

- посмотреть, что поменялось и когда;
- вернуть любую старую версию;
- попробовать что-то рискованное, не ломая рабочий вариант;
- работать вдвоём над одними файлами и не затирать друг друга.

**Git** — программа у вас на компьютере. **GitHub** — сайт, где хранится копия ваших файлов вместе со всей историей. Это разные вещи: Git работает и без интернета, а GitHub — как облачный диск специально для Git.

## Урок 1. Установка и первая настройка

### Установка

- **Windows:** скачать с [git-scm.com](https://git-scm.com) и ставить, нажимая «Далее». Вместе с Git поставится программа **Git Bash** — в ней и будем писать команды.
- **macOS:** открыть «Терминал» и набрать `git --version`. Если Git не установлен, система сама предложит его поставить.
- **Linux (Ubuntu):**

```bash
sudo apt install git
```

Проверка, что всё получилось:

```bash
git --version
```

Должно ответить что-то вроде `git version 2.45.0`.

### Представьтесь

Git подписывает каждое сохранение именем и почтой. Это делается один раз:

```bash
git config --global user.name "Ваше Имя"
```

```bash
git config --global user.email "you@example.com"
```

Почту лучше указать ту же, что на GitHub, — тогда сайт свяжет сохранения с вашим аккаунтом.

### Пара слов о терминале

Терминал — это окно, куда пишут команды текстом. Пугаться не надо, нужны всего три команды:

| Команда | Что делает |
|---|---|
| `pwd` | показать, в какой я папке |
| `ls` | показать файлы в папке |
| `cd имя_папки` | зайти в папку (`cd ..` — выйти на уровень выше) |

## Урок 2. Репозиторий: папка под присмотром

**Репозиторий** (коротко «репо») — обычная папка, за которой следит Git.

Создадим папку и включим в ней Git:

```bash
mkdir moy-proekt
```

```bash
cd moy-proekt
```

```bash
git init
```

Всё. Внутри появилась скрытая папка `.git` — там Git хранит всю историю. Её не трогаем и не удаляем: удалите её — пропадёт вся история.

Главная команда, которую стоит набирать постоянно:

```bash
git status
```

Она отвечает на вопрос «что сейчас происходит?»: какие файлы поменялись, что готово к сохранению, в какой ветке вы находитесь. Не понимаете, что творится, — пишите `git status`.

## Урок 3. Коммит: сохранение

**Коммит** — это и есть «сохранение». Снимок всех файлов в конкретный момент плюс подпись, что поменялось.

Сохранение в Git делается в два шага. Аналогия — отправка посылки:

1. **`git add`** — кладём вещи в коробку. Выбираем, какие изменения войдут в сохранение.
2. **`git commit`** — заклеиваем коробку и подписываем. Сохранение готово.

Коробку называют **индексом** или **staging area**. Зачем два шага? Чтобы можно было поменять пять файлов, а сохранить только два — те, что относятся к одной задаче.

### Пробуем

Создайте файл `privet.txt` с любым текстом, затем:

```bash
git status
```

Git покажет файл красным — он новый, Git за ним пока не следит.

```bash
git add privet.txt
```

```bash
git status
```

Теперь файл зелёный — он в коробке.

```bash
git commit -m "Добавил файл с приветствием"
```

Готово, первое сохранение. После `-m` в кавычках пишется сообщение — коротко, что вы сделали.

Добавить в коробку сразу все изменённые файлы:

```bash
git add .
```

Точка означает «всё в этой папке».

### Каким должно быть сообщение коммита

Пишите так, чтобы через полгода было понятно без открытия файлов:

- плохо: `правки`, `ещё`, `asdf`;
- хорошо: `Добавил вступление к сценарию про GTA`, `Исправил опечатки в главе 3`.

**Когда коммитить?** Каждый раз, когда сделан законченный кусочек работы. Маленькие частые коммиты лучше одного огромного: их легче понять и легче откатить.

## Урок 4. Смотрим историю и изменения

### История сохранений

```bash
git log --oneline
```

Пример ответа:

```
a3f9c21 Исправил опечатки в главе 3
7b2e810 Добавил вступление
1c0d4ff Добавил файл с приветствием
```

Слева — **хеш**, уникальный номер коммита. Полностью он длинный, но Git понимает и первые 7 символов. Сверху — самый свежий коммит.

Подробная история с авторами и датами — просто `git log`. Выход из длинного списка — клавиша `q`.

### Что именно я поменял

```bash
git diff
```

Покажет изменения, которые ещё **не** положены в коробку. Строки с `-` удалены, с `+` добавлены.

```bash
git diff --staged
```

Покажет то, что уже в коробке и уйдёт в следующий коммит.

Посмотреть, что было в конкретном коммите:

```bash
git show a3f9c21
```

## Урок 5. Отмена и откат

Самый важный урок для спокойного сна. Ситуации от простой к сложной.

### «Испортил файл, но ещё не сохранял — верните как было»

```bash
git restore privet.txt
```

Файл вернётся к последнему коммиту. **Осторожно:** несохранённые правки в этом файле пропадут насовсем.

### «Положил в коробку лишнее»

```bash
git restore --staged privet.txt
```

Файл вынется из коробки, а сами правки останутся на месте.

### «Закоммитил, но забыл файл или опечатался в сообщении»

```bash
git add забытый_файл.txt
```

```bash
git commit --amend -m "Правильное сообщение"
```

Последний коммит заменится исправленным. Делайте так, только если ещё **не отправили** коммит на GitHub.

### «Коммит был ошибкой, хочу его отменить»

```bash
git revert a3f9c21
```

Git создаст **новый** коммит, который делает ровно обратное. История не переписывается, поэтому это безопасно даже после отправки на GitHub.

### «Хочу просто посмотреть, как было раньше»

```bash
git switch --detach 7b2e810
```

Файлы в папке станут такими, какими были в том коммите. Посмотрели — возвращаемся обратно:

```bash
git switch main
```

### Про страшную команду `reset --hard`

В интернете часто советуют `git reset --hard`. Она откатывает всё и **безвозвратно стирает** несохранённую работу. Новичку она почти никогда не нужна: для большинства случаев хватает `restore` и `revert`.

## Урок 6. Ветки: параллельные вселенные

**Ветка** — отдельная линия истории. Представьте, что вы делаете копию сценария «на черновик», экспериментируете в ней, а основной вариант остаётся нетронутым. Получилось — переносите эксперимент в основной. Не получилось — выбрасываете черновик.

Главная ветка обычно называется `main` (в старых проектах — `master`).

```
main:        ●───●───●───────────●   ← основная версия
                      \         /
novaya-glava:          ●───●───●     ← эксперимент
```

### Команды

Какие ветки есть и где я сейчас (текущая отмечена `*`):

```bash
git branch
```

Создать ветку и сразу перейти в неё:

```bash
git switch -c novaya-glava
```

Перейти в существующую ветку:

```bash
git switch main
```

Удалить ветку, которая больше не нужна:

```bash
git branch -d novaya-glava
```

Совет: перед переключением веток закоммитьте текущую работу. Иначе Git либо откажется переключаться, либо перенесёт несохранённые правки с собой, и вы запутаетесь.

## Урок 7. Слияние и конфликты

### Слияние

Эксперимент в ветке удался, переносим его в `main`. Сначала переходим туда, **куда** вливаем:

```bash
git switch main
```

Затем вливаем ветку:

```bash
git merge novaya-glava
```

Всё, изменения из `novaya-glava` теперь в `main`.

### Конфликт — это не поломка

Конфликт случается, когда в двух ветках по-разному поменяли **одну и ту же строку**. Git не умеет угадывать, какой вариант правильный, и спрашивает вас. Файл с конфликтом выглядит так:

```
<<<<<<< HEAD
Сюжет начинается в Лос-Сантосе.
=======
Сюжет начинается в Сан-Фиерро.
>>>>>>> novaya-glava
```

- между `<<<<<<<` и `=======` — вариант из текущей ветки;
- между `=======` и `>>>>>>>` — вариант из вливаемой.

Что делать:

1. Открыть файл, оставить нужный текст (или объединить оба варианта), **удалить строчки-маркеры** `<<<<<<<`, `=======`, `>>>>>>>`.
2. Сохранить файл.
3. Сообщить Git, что конфликт решён, и закоммитить:

```bash
git add имя_файла
```

```bash
git commit -m "Слил ветку novaya-glava, решил конфликт"
```

Испугались и хотите отменить слияние целиком:

```bash
git merge --abort
```

Удобно решать конфликты в редакторе VS Code: он подсвечивает оба варианта и даёт кнопки «оставить этот», «оставить тот», «оставить оба».

## Урок 8. GitHub: копия в облаке

Пока вся история лежит только на вашем компьютере. Сломается диск — пропадёт всё. GitHub хранит копию в облаке и позволяет работать с другими людьми.

**Удалённый репозиторий** (remote) — копия репо на сервере. Обычно его называют `origin`.

### Четыре команды для связи с облаком

| Команда | Простыми словами |
|---|---|
| `git clone адрес` | скачать репо с GitHub к себе впервые |
| `git push` | отправить свои коммиты в облако |
| `git pull` | забрать чужие коммиты из облака к себе |
| `git fetch` | узнать, что нового в облаке, но пока ничего не менять у себя |

### Сценарий А: репо уже есть на GitHub

Нажимаете на странице репозитория зелёную кнопку **Code**, копируете адрес и:

```bash
git clone https://github.com/имя/репо.git
```

### Сценарий Б: репо есть у вас, надо выложить на GitHub

1. На github.com нажать **New repository**, придумать имя, ничего больше не отмечать, нажать **Create**.
2. Привязать облако к своей папке:

```bash
git remote add origin https://github.com/имя/репо.git
```

3. Отправить ветку `main` первый раз (`-u` запоминает связь, дальше хватит просто `git push`):

```bash
git push -u origin main
```

### Про пароль

При отправке GitHub спросит логин и пароль. **Обычный пароль от сайта не подойдёт** — нужен токен (Settings → Developer settings → Personal access tokens) или вход через браузер. Самый простой путь для новичка — программа [GitHub Desktop](https://desktop.github.com) или вход через VS Code: они настроят доступ сами.

### Распорядок дня

```bash
git pull
```

…работаете, делаете `add` и `commit`…

```bash
git push
```

Правило: **начинаете работу — `pull`, закончили — `push`.** Тогда меньше всего конфликтов.

## Урок 9. Pull Request: «посмотрите, можно влить?»

**Pull Request** (PR) — это предложение влить вашу ветку в `main`, оформленное на сайте GitHub. В нём видно все изменения, их можно обсудить и оставить комментарии к конкретным строкам.

Как это выглядит на практике:

1. Создали ветку: `git switch -c ispravleniya`.
2. Поработали, закоммитили.
3. Отправили ветку в облако:

```bash
git push -u origin ispravleniya
```

4. На GitHub появится жёлтая плашка с кнопкой **Compare & pull request**. Нажимаете, пишете, что сделано, жмёте **Create pull request**.
5. Коллеги смотрят, комментируют. Если надо поправить — правите в той же ветке и снова делаете `push`, PR обновится сам.
6. Когда всё хорошо — кнопка **Merge pull request**. Ветка влита в `main`.
7. У себя на компьютере обновляем `main`:

```bash
git switch main
```

```bash
git pull
```

Даже если вы работаете один, PR полезен: это удобный способ ещё раз просмотреть свои изменения перед тем, как они попадут в основную версию.

## Урок 10. Файл .gitignore

Некоторые файлы в Git класть не нужно: временные файлы, огромные видео, файлы с паролями. Чтобы Git их не замечал, создайте в корне репо файл `.gitignore` и перечислите их:

```
# временные файлы
*.tmp
.DS_Store

# тяжёлые исходники видео
*.mp4
*.mov

# секреты
.env
```

Звёздочка `*` значит «что угодно». `*.mp4` — все файлы с расширением mp4.

**Важно:** пароли и ключи в Git не кладут никогда. Даже если потом удалить файл, он останется в истории, и на публичном GitHub его найдут.

## Частые проблемы и что делать

**`fatal: not a git repository`**
Вы не в той папке. Проверьте `pwd`, перейдите в папку проекта через `cd`.

**`error: failed to push some refs` / `rejected ... fetch first`**
В облаке появились коммиты, которых нет у вас. Сначала заберите их, потом отправляйте:

```bash
git pull
```

```bash
git push
```

**Открылся странный редактор, и я не могу выйти**
Это редактор Vim — Git открывает его, когда вы забыли `-m` у коммита. Выход: нажать `Esc`, набрать `:wq` и нажать Enter. Чтобы впредь открывался понятный редактор, например nano:

```bash
git config --global core.editor nano
```

**`Your local changes would be overwritten`**
Git не хочет затирать несохранённые правки. Закоммитьте их (`git add .` и `git commit`), потом повторите команду.

**Закоммитил пароль**
Первым делом смените сам пароль или ключ — считайте его утёкшим. Удаление файла из истории — отдельная сложная процедура, тут лучше попросить помощи.

**Всё сломалось, ничего не понимаю**
Без паники. Наберите `git status` и прочитайте, что пишет Git, — он почти всегда подсказывает следующую команду. Пока вы не делали `reset --hard`, закоммиченная работа никуда не делась.

## Словарик

| Слово | Что значит |
|---|---|
| **Репозиторий (репо)** | папка, за которой следит Git, вместе со всей историей |
| **Коммит** | сохранение: снимок файлов плюс подпись |
| **Индекс / staging** | «коробка»: изменения, отобранные для следующего коммита |
| **Хеш** | уникальный номер коммита, вроде `a3f9c21` |
| **Ветка (branch)** | отдельная линия истории для экспериментов или задачи |
| **main / master** | главная ветка |
| **HEAD** | «вы здесь»: коммит, на котором вы сейчас стоите |
| **Слияние (merge)** | перенос изменений из одной ветки в другую |
| **Конфликт** | одна строка изменена по-разному в двух ветках, Git просит выбрать |
| **Remote / origin** | копия репо на сервере (обычно на GitHub) |
| **Push / Pull** | отправить в облако / забрать из облака |
| **Clone** | скачать репо к себе впервые |
| **Pull Request (PR)** | предложение на GitHub влить ветку в main |
| **.gitignore** | список файлов, которые Git должен не замечать |
